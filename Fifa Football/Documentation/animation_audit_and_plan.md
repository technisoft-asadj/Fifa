# Player animation: Phase 1 audit and implementation plan

Written 2026-11-17 for the locked specification in `animation_spec.md`. Nothing in this file has been implemented. Facts below come from reading the code in this repository today; items I could not check are marked **unverified**.

## 1. Audit: what exists

### 1.1 Characters and rig
- There are **no character models, no FBX files, no AnimationClips, no Animator Controllers, no Avatars, no Avatar Masks, no prefabs for players** in `Assets/` (searched). The only non-script assets are two ScriptableObjects for ball tuning, a formation, one `PlayerData`, materials and the scene.
- Each player is a scene GameObject with `CharacterController` + `PlayerController` + `PlayerVisual` (+ `PlayerAI`/input via `TeamController`). The scene is generated by an editor builder, not hand-authored.
- `Players/PlayerVisual.cs` (198 lines) builds a body at `Awake` from Unity primitives (capsules, spheres, cubes, ~14 parts, materials made in code) and animates it in `Update` with sine waves: leg swing and knee bend by speed, a forward lean, arm swing, and two canned poses (`PlayKick(rightFoot)`, `PlayTackle()`). The kick foot is chosen randomly (`Random.value > 0.25f`). It is a Transform hierarchy, **not a Humanoid rig**; there is no Animator, so none of the spec's Blend Tree, layer, mask, retargeting or IK machinery applies yet.
- Skin and hair come from a hash of the object name; the kit colour comes from `SetKit`. The network guest draws players as plain capsules (`Net/NetClientView.cs`), not `PlayerVisual`.

### 1.2 Movement (`Players/PlayerController.cs`, 295 lines)
- Kinematic `CharacterController` movement driven from `Update` (not a fixed step): `planarVelocity` moves toward `dir * topSpeed` by `AccelerationMs2`, rotation by `RotateTowards` at `TurnRateDegPerSec`. Constant `motion.y = -2` (no real gravity, **no jump, no airborne state, no landing**).
- Speeds and rates come from `PlayerData` (ScriptableObject, attributes 1-99: pace, acceleration, sprintSpeed, shooting, passing, dribbling, ballControl, agility, stamina, strength). **No preferred foot, no archetype, no animation profile.**
- Stamina: `StaminaModel` (sprint drains, exhausted below 0, recovers to 25 %).
- Because motion is script-driven and animation does not drive the body, correct foot-sliding behaviour needs the animation's stride to be matched to the actual speed, not root motion (see 4.2).

### 1.3 Ball interaction
- `Ball/BallController.cs`: Rigidbody ball with custom drag, Magnus force and rolling resistance in `FixedUpdate`; ball position read from `rb.position`. Good: the ball is **not** glued to the foot, which matches the spec.
- Dribbling = "touch" kicks: when in range, in front, grounded and moving, `KickBall` pushes the ball (speed scales with player speed; cooldown scales with `ballControl`). There is no first touch, trap, receive or shield behaviour.
- Pass and shoot (`Strike`) apply the impulse **the instant the button is read**; the kick animation is played afterwards for show. Power, aim error and loft come from `PlayerData`. There is no foot choice, no contact timing, no wind-up, no curve control beyond random spin.
- Tackle: a 0.22 s forward lunge, a win probability from `strength`, a foul check by overlap sphere (`CheckFoul`). Goalkeepers: `GoalkeeperModel` decides catch/parry from shot speed and distance; the dive is a lunge reusing the tackle pose.

### 1.4 Input (`Input/*`)
- `IPlayerInput`: `Move`, `MoveIsWorldSpace`, `Sprint`, `PassPressed`, `ShootHeld`, `ShootReleased`, `TacklePressed`, `SwitchPressed`, `AimWorld`, `ActionPower`. That is the whole vocabulary shared by keyboard, touch, AI and network (`RemoteInput`).
- `TouchControls`: one floating joystick and five fixed buttons (Shoot, Pass, Sprint, Tackle, Switch). Only scale and opacity are adjustable (saved in PlayerPrefs). No context-sensitive buttons, no layouts, no drag-to-reposition.
- Missing against M3-M5: THROUGH, FINESSE, LOB/CROSS, SKILL, SLIDE, CONTAIN, PRESS, JOCKEY, GK RUSH and the keeper set.

### 1.5 Networking (`Net/*`)
- Server-authoritative UDP, snapshots every 3 frames, `NetCodec.PlayerState` = x, z, yaw, speed, flags (`Diving`, `Exhausted`) = 7 bytes per player, 22 players, 174-byte snapshot. Input frames are 5 bytes with sequence numbers; server acks (type 7) exist for later prediction.
- **There is no action id, action time or animation id in the snapshot.** The client has no prediction yet (guest sees the host's world interpolated). Ball interaction state is not sent.
- Online play today: 1v1 on the same Wi-Fi (host plays home, one guest takes an away outfielder). 11v11 online would need many guests; not built.

### 1.6 Other facts that constrain the plan
- Packages: no `com.unity.animation.rigging` (free Unity package; can be added from the Package Manager). `com.unity.ugui` 2.0 (TextMeshPro now imported). Input System 1.17.
- Platforms: Android ARM64 builds work and run on the Infinix X6881; ARMv7 not enabled; iOS cannot be built on this Windows PC.
- Performance on device: not measured. The current 22 primitive-body players run at an unmeasured frame rate on the phone.
- Tests: EditMode 154, PlayMode 76 (5 gated probes Inconclusive). Several PlayMode tests depend on the kick/tackle timing and on `PlayerVisual` existing, so changes here must keep them green.
- Determinism: the plan.md "fixed-step, command-driven core" goal is only partly met (players update in `Update`, ball in `FixedUpdate`). Action timing added now must use `SimClock`/fixed ticks, not animation playback.

## 2. Honest feasibility of the "elite" target
- **I cannot author motion-capture quality animation.** Elite realism comes from real mocap clips. Without clips the best I can do is the current procedural look. So this project is blocked on the owner downloading free clips (section 6). I will not pass off procedural motion as realistic.
- Mixamo has a limited football set and needs an Adobe account (free) and a manual download. The Anderson Rohr soccer pack and Kevin Iglesias' free pack are the other named sources. Whether their contents cover every category (e.g. goalkeeper dives, celebrations, left-foot variants) is **unverified until the files are in hand**; anything missing is recorded as missing.
- Left/right foot: the spec forbids blindly mirroring. A mirrored kick is acceptable only if the contact frame is checked; otherwise it is marked as a known limitation.
- Individual identity across 22 players is achievable with shared clips plus profile parameters (stride, lean, arm swing, turn style, kick technique choice, celebration weights) and a few alternative clip sets. It will not be 22 unique mocap performances.
- iOS 64-bit and Amazon: code stays platform neutral; iOS cannot be built here; Amazon uses the same APK.
- ARMv7: the Unity 6 player may not offer it in this editor install; unverified. Plan.md already flags it as a risk.

## 3. Principles for the build
1. **Gameplay never depends on the Animator.** The simulation (server) decides when a kick, tackle or save happens from its own timers; the animation is presentation that follows the sim state. This keeps the server cheap (no Animator needed), keeps online deterministic and lets a procedural fallback exist.
2. **One mover.** `PlayerController` stays the only thing that moves the body. No root motion for locomotion. Animation speed is matched to the real speed.
3. **Contact-time actions.** A kick is a short sequence (wind-up, contact, follow-through) with data-driven times; the impulse is applied at the contact tick, and the animation is authored/blended so the foot meets the ball there.
4. **Shared clips + profiles**, not copies.
5. **Procedural fallback stays** (`PlayerVisual`) behind an interface so tests, the server, culled/far players and a first run without assets keep working.
6. **Small network additions only**: action id + phase and a few flags; profile ids come from deterministic data, never per-frame.

## 4. Target architecture (mapped onto what exists)

### 4.1 Components
| Spec suggestion | Plan |
|---|---|
| PlayerController | Keep. Stays the movement owner and the entry point for input. Gains an action state machine call-out (below) |
| PlayerMovement | Extract acceleration, turning, ground and (new) jump/airborne state from `PlayerController` into a plain class (EditMode-testable) only if it keeps `PlayerController` small; otherwise leave |
| PlayerAttributes | `PlayerData` stays; add `PlayerProfile` data (preferred foot, weak-foot factor, archetype, animation profile id, celebration weights) |
| PlayerStamina | Exists as `StaminaModel` |
| PlayerBallController / Shooting / Passing / Defending / SkillMoves | New pure-C# action definitions (`PlayerActions`): data for each action (id, wind-up, contact time, recovery, foot rule, power/accuracy function). `PlayerController` runs an `ActionState` (None / WindUp / Contact / Recovery) and applies effects at contact. Avoids many MonoBehaviours |
| PlayerAnimationController | New MonoBehaviour next to `PlayerVisual` that reads a read-only `PlayerAnimState` snapshot (local velocity, speed, turn rate, action id, action normalised time, foot, airborne, stamina) and drives an Animator. `PlayerVisual` implements the same presentation interface for the fallback |
| PlayerIKController | Later, small: foot-ground IK and a look/ball IK, only if profiling allows |
| PlayerNetworkState | Extend `PlayerState` with action id/phase byte(s); see 4.4 |

### 4.2 Locomotion without foot sliding
- Script-driven body, so the Animator receives `speed` (m/s) and a local-space `moveX/moveY` (strafe/backward). Blend Tree thresholds are in m/s and clips are authored/measured so a clip's foot speed equals its threshold; the Animator `speed` multiplier adjusts playback by `actualSpeed / clipSpeed` so feet do not skate.
- 2D freeform directional Blend Tree for walk/jog/run/sprint with strafe and backward; separate turn-in-place and 90/180 pivot states driven by the angle between facing and desired direction; start/stop transitions from acceleration sign.
- Turn rate is limited by `agility`; body lean from lateral acceleration (procedural additive).

### 4.3 Actions and the animation layers
- Base layer: locomotion + idle. Upper-body layer (Avatar Mask) for arm balance, receiving and shielding. Action layer for kicks, tackles, jumps, saves with full-body override. Additive layer for lean, breathing and tired posture. Keeper uses its own controller (or an override).
- Animation events are used for sound and cosmetic effects only. Gameplay timing comes from the sim.
- Jump/header: add a vertical state (`airborne`, vertical velocity, gravity) to `PlayerController`; the ball interaction at the header contact time is decided by the sim; landing recovery is a timed state that limits movement. New gameplay behaviour requires new tests and tuning; the balance tests must stay green.

### 4.4 Network animation synchronisation (design, not built)
- `PlayerState` today: x, z, yaw, speed, flags. Add: `action` (byte: id, 0 = none), `actionPhase` (byte, 0-255 of normalised time or elapsed ticks), and flags for airborne / on-ground (fell). About +2 bytes per player = +44 per snapshot (174 -> 218 bytes); still far below the 20 KB/s target.
- Clients run the same locomotion blend from interpolated velocity/yaw and start/stop actions from the action byte. An action that arrives mid-way starts at the given phase, so late packets do not replay it twice (action ids are per-player sequence numbers to prevent duplicates).
- Profile ids: derived from the player's index and the match roster (deterministic), sent once in the welcome/match setup, never per tick.
- 22-player case is the same message; cost is only more Animators, handled by culling and LOD (section 7).

### 4.5 Individual profiles (P1-P6)
`PlayerProfile` (ScriptableObject or plain data table, identified by an integer id) holds: archetype; run style id (selects an Animator override or a clip set and stride/lean/arm-swing multipliers); sprint style id; acceleration character (curve shape modifier); turn style id; dribble style id (touch spacing, body lean); preferred foot (Right / Left / Both) and weak-foot factor; shooting technique ids and weights; passing technique id; jump style id; celebration weights; recovery speed; defensive stance id. Attributes (`PlayerData`) feed the quality and error of the same actions; the profile feeds their **look**.
- First polish ONE player prototype to the quality bar, then derive 5+ profiles, then the squad (amendment 10).

## 8. Risks
- No free clip set may cover every action in the spec (goalkeeper and celebration clips especially). Missing ones are listed in `known_bugs.md` rather than faked.
- Retargeting/foot-contact quality of free mocap on a different skeleton can look wrong; needs inspection on the model, possibly Blender cleanup.
- Changing the timing of kicks and tackles changes the balance of the AI match (the project has tuned it); expect test and tuning churn.
- Jump/header adds a new physics state that interacts with the ball, keeper and fouls.
- Animator cost for 22 players on low-end phones is unknown.
- Licensing: Mixamo terms allow use inside a game but forbid redistributing the raw files; do not commit raw Mixamo FBX to a public repository without checking. The repo is private/unknown: **decision needed**.
